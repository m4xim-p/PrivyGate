# PrivyGate Engineering Rules

Этот файл действует для всего репозитория.

## Обязательный preflight перед любыми изменениями

Перед изменением любого кода, конфигурации, API, тестов, Docker-файлов или
документации инженер или AI-агент **обязан** выполнить preflight. Нельзя
начинать изменение файлов до его завершения.

Preflight выполняется **один раз** перед началом задачи и повторяется, только
если изменился scope задачи либо один из канонических документов.

1. Прочитать в указанном порядке:
   - `docs/source/README.md` — иерархия и provenance внешних требований;
   - `docs/source/track-specification.txt` — полное ТЗ, включая нормативные Приложения A/B;
   - `docs/source/organizer-clarifications.txt` — сохранённые ответы организаторов;
   - `docs/source/project-owner-notes.md` — подтверждения без приложенного первичного transcript;
   - `SECURITY.md` — обязательный merge-blocking security checklist;
   - `CONTRIBUTING.md` — командный workflow и ownership hotspot-файлов;
   - `docs/requirements.md` — цели, ограничения и матрица покрытия;
   - `docs/architecture.md` — границы компонентов и разрешённые зависимости;
   - `docs/evaluation-contract.md` — неизменяемый контракт AlfaSonar `/process`;
   - `docs/security.md` — подробная модель угроз и правила обработки PII;
   - `docs/roadmap.md` — текущие приоритеты, но не источник требований;
   - релевантные ADR из `docs/adr/`.
2. Перед реализацией назвать, какие документы и ограничения относятся к текущей
   задаче.
3. Проверить, не создаёт ли изменение второй PII pipeline или дублирование
   существующей логики.
4. Проверить соответствие security policy и контракту `/process`.
5. При противоречии документов **не выбирать самостоятельно удобный вариант**:
   остановиться и сообщить о конфликте.

Результат preflight зафиксировать в описании задачи, PR или первом рабочем
комментарии агента: перечислить применимые документы, ограничения и
затрагиваемые hotspot-файлы.

### Непереговорные источники

Приложения A/B из `docs/source/track-specification.txt`, подтверждённые уточнения
организаторов и `SECURITY.md` являются одновременно
непереговорными ограничениями. Ни один из них не может быть нарушен ради
другого. При обнаружении конфликта остановиться и сообщить о нём.

`process_api.yaml`, requirements, architecture, evaluation contract и ADR являются
производными документами и должны трассироваться к `docs/source/`. Уточнение из чата
может переопределять неоднозначную формулировку ТЗ только если его текст сохранён в
репозитории; неподтверждённые предположения не переводятся в Accepted ADR.

### Приоритет остальных источников при конфликте

1. `docs/requirements.md` и `docs/security.md`;
2. `docs/architecture.md` и принятые ADR;
3. `docs/roadmap.md`.

`CONTRIBUTING.md` определяет командный workflow и ownership hotspot-файлов.
После изменения обновить документацию, ADR или requirements matrix, если
фактическое состояние изменилось.

## Непереговорные правила

- Никогда не логировать raw PII, prompt, mask mapping или полное тело запроса.
- `MOCK_LOG_REQUEST_BODY` разрешён только локально и только с синтетическими данными.
- Новые детекторы реализуют `PIIDetector` и возвращают `PIIMatch` с offsets
  исходного текста.
- Не добавлять regex, NER-вызовы и PII-логику непосредственно в endpoints.
- `/process` и `/v1/chat/completions` должны использовать одно общее PII-ядро.
- Не дублировать detection, overlap resolution, masking или demasking.
- Для AlfaSonar допустимы typed placeholders любой длины; не создавать
  format-preserving masking только ради scorer.
- False negative штрафуется сильнее false positive, но blanket masking и захват
  служебных слов запрещены.
- `/process` принимает проверяющую систему без обязательных auth headers и использует
  default evaluation profile; product endpoints следуют allowlist policy.
- На demasking `/process` приходит ровно ранее выданная маска, а не изменённый LLM текст.
- Новая PII-категория требует positive, negative, case/format, overlap и
  round-trip tests.
- Контракт `/process` нельзя менять ради внутреннего удобства реализации.
- Новая runtime-зависимость требует обоснования в PR; архитектурная зависимость — ADR.
- Производительные оптимизации принимаются только вместе с воспроизводимым benchmark.
- Сохранять DRY/KISS и ограничивать сложность функций: код проходит автоматический
  анализ complexity, deprecated APIs и conventions.
- Локальный NER не должен передавать пользовательский текст внешним сервисам.
- При недоступности обязательного detector применяется fail-closed поведение.

## Правила изменений

- Сначала найти существующую точку расширения; не создавать параллельный pipeline.
- Не смешивать API adapter, PII domain logic, state storage и upstream LLM client.
- Сохранять обратную совместимость `/v1/chat/completions`, если задача явно не
  меняет публичный контракт.
- Учитывать незакоммиченные изменения других инженеров и не перезаписывать их.
- Обновлять `docs/requirements.md`, если меняется статус требования.
- Обновлять ADR, если меняется принятое архитектурное решение.

## Проверка

- Unit-тесты не должны загружать реальную Transformers-модель; использовать fake backend.
- Перед передачей изменений запускать релевантные тесты, затем полный `pytest`.
- Для `/process` обязательны тесты idempotency, retries, concurrency, TTL,
  ACTIVE/COMPLETED lifecycle, conflict handling, entry/byte overload и отсутствия PII
  в логах.
- Тестовые PII должны быть синтетическими; использовать reserved example-домены и
  тестовые номера карт.
