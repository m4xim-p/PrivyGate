## 1. Критерии оценивания (максимум 30 баллов)

Итоговая оценка — сумма баллов по 8 критериям.

| # | Критерий | Баллы |
|---|---|---|
| 1 | Качество идентификации и маскирования ПДН | 0-6 |
| 2 | Корректность демаскирования | 0-3 |
| 3 | Точность отнесения к ПДН и устойчивость к вариациям написания | 0-4 |
| 4 | Гибкая настройка и расширяемость | 0-4 |
| 5 | Производительность и SLA | 0-4 |
| 6 | Безопасность, логирование и метрики | 0-3 |
| 7 | Расширенные сценарии (доп. возможности) | 0-3 |
| 8 | Качество демо и презентации | 0-3 |

### Общие принципы

- Жюри оценивает качество и скорость работы модуля (идентификация → маскирование →
  демаскирование), гибкость настройки и качество демо, а не объём кода.
- Production-готовность не оценивается: решение должно работать как демо-прокси в
  цепочке «система-потребитель → Модуль → LLM».
- Критерии рекомендуют обращать внимание на ключевые моменты, но не обязывают
  следовать жёсткому формату: допускается свободная экспертная оценка в рамках
  указанного диапазона баллов.
- Критерии проверяются запросами к решению по установленному датасету (17 категорий,
  от персональных данных до данных карт).
- Утечка немаскированных ПДН в LLM-запрос/ответ на демо-сценариях — существенное
  снижение оценки по всем связанным критериям.

### 3.1. Качество идентификации и маскирования ПДН (0-6)

- Покрыто максимум типов ПДН из перечня в задании (полнота покрытия — основа балла).
- Маска действительно делает обработанный текст нечитаемым и невосстанавливаемым.
- Нет пропусков: ПДН из текста не уходит в LLM в открытом виде.
- Оценка свободная: за близкие к правилам маски (допустимые вариации) балл не
  снимается, за систематические пропуски целых типов — снижается существенно.

### 3.2. Корректность демаскирования (0-3)

- Демаскированный текст совпадает с оригиналом, позиции знаков сохранены.
- Демаскирование доступно только авторизованной/настроенной системе (см. 3.4).
- Если демаскирование не реализовано — 0, без возможности компенсации другими
  критериями; реализация через токенизацию/детокенизацию засчитывается наравне с
  классическим демаскированием.

### 3.3. Точность отнесения к ПДН и устойчивость к вариациям написания (0-4)

- Ложные срабатывания отсутствуют или минимальны (не является ПДН — не маскируется).
- Определение не зависит от регистра.
- Распознаются вариации: форматы дат, написание даты текстом, разделяющие слова
  («серия … номер …»).
- Свободный критерий: жюри вправе оценить общую «умность» эвристики/ML-подхода.
- Проверка на «ловушках»: поэт Александр Пушкин, адрес отделения Банка.

### 3.4. Гибкая настройка и расширяемость (0-4)

- Если у решения нет README с описанием и возможностями настроек — критерий
  выставляется в 0 баллов.
- Настройка списка систем-потребителей (вкл/откл обращение в модуль).
- Настройка перечня типов ПДН и самого факта маскирования в зависимости от системы.
- Наличие/отсутствие демаскирования по системе.
- Расширение списка идентифицируемых ПДН без переписывания ядра (конфиг, плагины,
  справочник).

### 3.5. Производительность и SLA (0-4)

- Ориентир: Latency ≤ 0.5 с при RPS 1000 — целевой уровень; честная оценка своего
  latency с подтверждением метриками засчитывается даже без полного нагрузочного теста.
- Обработка крупных текстов (до 100 000 токенов) без падения.
- RPS 2000 при том же latency — повышенный уровень (можно учесть и здесь, и в 3.7).
- Если нагрузочное подтверждение отсутствует — балл снижается, но не обнуляется при
  наличии корректной архитектуры.

### 3.6. Безопасность, логирование и метрики (0-3)

- Логирование выявленных типов ПДН по каждому запросу; подробное логирование этапов
  обработки.
- Метрики Latency / RPS / TPS присутствуют.
- Ограничение круга систем, обращающихся в сервис (allowlist, ключи, mTLS — на уровне
  демо-подтверждения).
- Нет утечек ключей/реальных ПДН в артефактах сдачи; шифрование хранилища соответствия
  — по усмотрению жюри.
- Корректная обработка ошибок: понятные ответы при невалидном запросе, деградация при
  недоступности компонентов.

### 3.7. Расширенные сценарии (доп. возможности) (0-3)

Свободный критерий. Засчитывается любое из (по 1 баллу за уверенно показанное,
максимум 3):

- Токенизация/детокенизация или замена синтетическими данными.
- Настройка вида маскирования/токенизации под систему.
- RPS 2000 при Latency ≤ 0.5 с.
- Идентификация документов, удостоверяющих личность, кроме паспорта РФ.
- Контекстное маскирование: маска только при комбинации типов ПДН (PIN + номер карты),
  с настраиваемым правилом.

### 3.8. Качество демо и презентации (0-3)

- Есть короткое объяснение принципа работы и архитектуры (1–2 минуты).
- Есть схема: Система-потребитель → Модуль (идентификация → маскирование → LLM →
  демаскирование) → Потребитель.
- Ответы на вопросы лаконичны, аргументированы, корректны.

## 2. Обязательные артефакты на сдачу

1. Рабочий демо-сервис-прокси, запускаемый по инструкции (README), с точками входа для
   запросов в LLM и обратно.
2. Инструкция для жюри по проверке: как отправить тестовый текст, как получить
   замаскированный/демаскированный результат, где посмотреть логи и метрики.
3. Схема архитектуры и настройки: системы-потребители, конфигурируемые типы ПДН и
   правила маскирования.
4. Сведения о производительности (замеры/нагрузочный тест) и список реализованных
   дополнительных возможностей.
5. Описание ограничений решения и плана развития после хакатона.

## 3. Критерии финалистов (оценка на встрече)

Каждый из четырёх критериев оценивается по шкале 1 / 2 / 3:

| Балл | Значение |
|---|---|
| 1 | Ниже ожиданий — есть сомнения |
| 2 | Уверенно — сделано как надо |
| 3 | Впечатляет — заметно выше остальных |

Стоп-сигнал: если на живом демо в запрос к внешней модели (LLM) ушли реальные
персональные данные без маскирования — это не «минус балл», а провал ключевой
функции. Утечка перевешивает любые технические достоинства.

### 1. Доверие: решение действительно защищает данные

Вопрос себе: готов ли я поставить это между рабочими системами и внешней моделью (LLM)?

Хорошие знаки:
- На демо ни один фрагмент персональных данных не ушёл в LLM в открытом виде.
- Замаскированный текст корректно возвращается в исходный вид — ничего не «потерялось».
- Не паникует на ловушках: поэт Александр Пушкин и адрес офиса — не данные клиента.

Тревожные знаки:
- Хоть одна утечка данных во время показа.
- Демаскирование работает «примерно» или не работает вовсе.
- Маскирует всё подряд — и ломает смысл запроса к LLM.

### 2. Внедряемость: это можно поставить в реальные системы

Вопрос себе: что мешает запустить с этой командой пилот через месяц?

Хорошие знаки:
- Скорость работы показывают цифрами и метриками, а не обещаниями.
- Маскирование включается, выключается и настраивается под каждую систему-потребителя
  — без правки кода.
- Новые типы данных добавляются через настройку или справочник, а не правкой ядра.

Тревожные знаки:
- «Производительность и настройки — это потом».
- Логика жёстко зашита под один сценарий демо.
- Нет способа управлять поведением по разным системам-потребителям.

### 3. Сила решения: чем это лучше базового и конкурентов

Вопрос себе: что здесь есть, чего нет у других, и нужно ли это бизнесу?

Хорошие знаки:
- Осмысленные возможности сверх базы: токенизация или синтетика, маскирование по
  комбинации данных, документы кроме паспорта РФ, повышенная нагрузка.
- Команда понимает, где её подход даёт сбой, и говорит об этом честно.
- Каждая «фича» имеет понятную бизнес-причину.

Тревожные знаки:
- Возможности добавлены «для галочки», без объяснения зачем.
- Не могут связать решение с реальной пользой для бизнеса.
- Впечатляет только на словах — в демо этого нет.

### 4. Команда: справятся ли они дальше

Вопрос себе: доверил бы я этой команде развивать продукт после хакатона?

Хорошие знаки:
- За 1–2 минуты объясняют суть и архитектуру так, что понятно без ИТ-бэкграунда.
- На вопросы отвечают по существу и не боятся признать ограничения.
- Понимают не только технологию, но и цену ошибки при работе с данными.

Тревожные знаки:
- Путаются в собственном решении.
- Уходят от неудобных вопросов или отвечают заготовками.
- Знают технологию, но не понимают саму проблему защиты данных.

## Связь с автопроверкой

По уточнению организаторов (`organizer-clarifications.txt`): автоматическая проверка
дополняет оценку жюри и не влияет на баллы напрямую, однако на основании её результатов
могут быть снижены баллы по определённым критериям (например, по критерию 3.1 «Качество
идентификации и маскирования ПДн», если при автопроверке качество маскирования низкое).
